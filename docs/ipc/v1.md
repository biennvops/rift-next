# Rift local IPC protocol v1

Foundation M4 local control uses a protocol that is deliberately independent from the
Rift network protocol (`rift/1`). Its protocol version is `1`; it has no ALPN and is never
served on a TCP or other network interface.

Machine-readable exact encodings are in
[`v1-vectors.json`](v1-vectors.json). They pin semantic JSON, exact UTF-8 payload bytes,
and the complete length-prefixed frame for authentication, status, peer management,
pairing, and session events.

## Local transports

- Linux and macOS use a Unix-domain socket beneath the daemon's private data directory.
  The socket mode is `0600`.
- Windows uses a unique per-runtime local named pipe. There is no TCP fallback.

Clients discover the active local endpoint through the atomically published private
`runtime.json` descriptor. Its schema version is also currently `1`, but descriptor and
IPC versions are separate constants. The descriptor contains the daemon PID, a fresh
runtime ID, transport/address, and a fresh bearer token. It is local process discovery,
not remote peer discovery.

## Framing and bounds

Every message is exactly:

```text
4-byte unsigned big-endian JSON payload length
UTF-8 JSON payload
```

The maximum payload is 262,144 bytes (256 KiB). Implementations must read and validate the
four-byte prefix before allocating payload-sized storage, then read exactly the declared
payload. Oversized, truncated, non-UTF-8, malformed JSON, unknown message types, and fields
outside the v1 schema are connection-local protocol failures.

The daemon additionally bounds local clients, outstanding requests per client, request
processing concurrency, and each client's outgoing event/response queue. A client that
lags a bounded event queue is disconnected.

`DeviceId` fields use the current `rift-core` Serde JSON representation: an exact array of
32 unsigned byte values. Pairing attempt IDs, session IDs, and request IDs are unsigned
64-bit integers. Attempt/session IDs are runtime-local and reset after daemon restart.

## Authentication

Every daemon launch obtains a new random 32-byte bearer token from the operating-system
CSPRNG. The first client frame must be:

```json
{"type":"authenticate","version":1,"token":"64-lowercase-hex-characters"}
```

The daemon validates the complete token without revealing a matching prefix. Wrong
versions, malformed/non-lowercase tokens, wrong tokens, authentication timeout, or any
other first message close only that client. No command, status, response, or event is sent
before authentication. Success is acknowledged as:

```json
{"type":"authenticated","version":1}
```

Tokens are capability material: clients may read them from private `runtime.json`, but
implementations must not log them or include them in `Debug` output. Tokens are not
persisted across daemon launches.

## Requests and responses

Authenticated requests carry a client-selected correlation ID:

```json
{"type":"request","id":42,"request":{"type":"get_status"}}
```

Successful and failed responses preserve that ID:

```json
{"type":"response","id":42,"result":{"type":"status","status":{...}}}
{"type":"error","id":42,"error":{"code":"invalid_request","message":"..."}}
```

Request IDs permit responses and asynchronous events to coexist. Clients must not infer
response identity from ordering.

Protocol v1 operations are:

- `get_status`
- `list_peers { after, limit }` (exclusive `DeviceId` cursor, server cap 128)
- `list_sessions`
- `list_pending_pairings`
- `confirm_pairing { attempt_id, accepted }`
- `revoke_peer { device_id }`
- `forget_peer { device_id }`
- `disconnect_session { session_id }`

There is intentionally no `trust_peer` request. The only operation that can cause
Unknown → Trusted is `confirm_pairing`, which acts on a live M3 `PendingPairing` and still
requires both network peers' positive decisions plus durable trust persistence.

`get_status` returns the daemon version, persistent public `DeviceId`, bounded local name
and platform, explicit runtime state, active-session count, pending-pairing count, and
whether pairing is enabled. It never returns the Iroh secret key, bearer token, trust
journal contents/path, or raw network state.

Peer listing is deterministic and paginated. The server may reduce any requested page to
128 entries and returns an optional exclusive `next_cursor`. Session and pending-pairing
lists cannot exceed their configured runtime registry bounds. Pending entries expose only
the authenticated identity, bounded display metadata, six-digit comparison code, and
saturating confirmation time remaining; pairing nonces, commitments, and network pairing
IDs remain private.

## Events

Authenticated clients may receive these bounded events between responses:

- `pairing_pending`
- `pairing_resolved`
- `session_opened`
- `session_closed`
- `trust_changed`
- `daemon_shutting_down`

Events contain presentation and runtime-registry data only. They never contain raw Rift
network frames, Iroh connection/address objects, nonces, commitments, secret key bytes, or
the IPC token.
