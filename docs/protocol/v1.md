# Rift production protocol v1

## Scope and ALPN

Production Rift protocol v1 is carried over an authenticated Iroh QUIC connection. Its
ALPN is the single canonical byte string `rift/1`, exported by `rift-protocol::ALPN`.
The Prototype 0 ALPN is unrelated and remains frozen in `rift-spike`.

A successful v1 bootstrap authenticates the cryptographic endpoint identity and binds
that identity to the application Hello. It does not by itself authorize an operation
or create durable peer state. Unknown peers may proceed only through the bounded pairing
protocol described below.

`rift/1` remains pre-release while the Foundation milestones establish its initial
message set. M3 appends pairing messages without changing the M2 Hello, Ping, or Pong
wire discriminants or conformance bytes.

## Control framing

The production control stream is a bidirectional QUIC stream. Every control message is
one complete frame:

```text
+----------------------+-----------------------------+
| 4-byte BE u32 length | Postcard payload            |
+----------------------+-----------------------------+
                         length bytes
```

The length excludes the four-byte prefix. The maximum payload length is
`1,048,576` bytes (`MAX_CONTROL_FRAME_LEN`). A receiver reads exactly four prefix
bytes, rejects a declared length above the maximum before allocating, allocates no more
than the declared bounded payload, reads exactly that payload, and then decodes one
Postcard value that must consume every payload byte. Trailing payload bytes are rejected.
A writer encodes first, checks the encoded length, and writes the prefix and complete
payload.

The length prefix is fixed-width big-endian. Postcard's wire representation is part of
this protocol contract; changing the serialization dependency or its configuration
requires deliberate compatibility review and updated vectors.

## Message schema

The Postcard enum variants are ordered as follows:

```rust
ControlMessage::Hello(Hello)                         // variant index 0
ControlMessage::Ping { nonce }                       // variant index 1
ControlMessage::Pong { nonce }                       // variant index 2
ControlMessage::PairingRequest { pairing_id, commitment }
                                                       // variant index 3
ControlMessage::PairingResponse { pairing_id, commitment }
                                                       // variant index 4
ControlMessage::PairingDecision { pairing_id, accepted }
                                                       // variant index 5
ControlMessage::PairingComplete { pairing_id }         // variant index 6
ControlMessage::PairingReveal { pairing_id, nonce }    // variant index 7
```

`Hello` fields are serialized in this order:

```rust
Hello {
    protocol_version: u16,
    device_id: DeviceId,       // exactly 32 public bytes
    device_name: String,
    platform: String,
    capabilities: Vec<Capability>,
}
```

`DeviceId` is the 32-byte public cryptographic Rift device identity. It contains no
secret key material. Postcard serializes it as exactly the transparent `[u8; 32]`
contents.

`Capability` is a forward-compatible numeric identifier serialized as a Postcard
`u16`. Unknown numeric values are valid, retained in the decoded Hello, and not acted
on by a v1 implementation. Known identifiers are `1` (`BLOB_TRANSFER_V1`, reserved and
not advertised because production blob transfer does not exist) and `2` (`PAIRING_V1`).
A session implementation advertises `PAIRING_V1` when pairing support is enabled. An
unknown peer that did not advertise it cannot be paired through this implementation.

The semantic bounds are:

| Field | Bound |
| --- | ---: |
| `device_name` UTF-8 bytes | 128 |
| `platform` UTF-8 bytes | 64 |
| `capabilities` entries | 64 |
| encoded control payload | 1 MiB |

These are byte/count bounds, not normalization or localization rules. A receiver checks
encoded string lengths and capability counts during deserialization, before allocating
owned strings or allowing capability storage to grow beyond its bound. Metadata is also
validated before a Hello is accepted.

## Bootstrap ordering

The side initiating the connection opens the first bidirectional control stream. Both
peers send their Hello before waiting for the peer's Hello, so neither side is required
to wait for the other's entire handshake.

```text
Initiator A                              Acceptor B
    |                                        |
    |--- authenticated QUIC, ALPN rift/1 -->|
    |                                        |
    |==== open bidirectional control =======>|
    |                                        |
    |--------- Hello(A) ------------------->|
    |<-------- Hello(B) --------------------|
    |                                        |
    | validate B version, bounds, ID        |
    |                         validate A     |
    |                         version, bounds, ID
    |                                        |
    |          bootstrap complete            |
    |                                        |
    |--------- Ping(nonce) ---------------->|
    |<-------- Pong(nonce) -----------------|
    |                                        |
    |================ close ================>|
```

For each received Hello, the transport-authenticated remote Iroh endpoint ID is
converted to `DeviceId` and checked against `Hello.device_id`. A mismatch is an
`IdentityMismatch` failure and the disposable connection is closed. The local
transport constructs its outbound Hello from its own endpoint identity; application
metadata cannot replace that identity in the production bootstrap API.

## Version and failure behavior

The only supported version in this document is `protocol_version = 1`. An unsupported
version is rejected explicitly as `UnsupportedProtocolVersion`; there is no silent
downgrade or fallback to an older Rift protocol.

The protocol exposes typed errors for encoding, decoding, truncated prefixes, truncated
payloads, oversized frames, trailing payload bytes, malformed metadata, too many
capabilities, unexpected message ordering, unsupported versions, identity mismatch,
I/O writes, and Hello timeouts. A failed bootstrap closes/discards its connection and
does not poison the endpoint. The endpoint has explicit deadlines for connect,
control-stream establishment, and Hello exchange. No automatic retry or reconnect loop
is part of v1.

`Ping` and `Pong` are one-shot control primitives used to prove that the stream remains
usable after bootstrap. They are not a background heartbeat service. A Pong must carry
the matching nonce. Because timed cancellation of framed stream I/O can leave partial
bytes consumed or written, any post-bootstrap control timeout, framing error, or
sequencing error poisons and closes that disposable connection. Later control calls on
the same wrapper fail without touching the stream; callers must establish a fresh
connection.

## Pairing protocol

Pairing has explicit initiator and responder roles. A pairing ID is exactly 16 bytes,
each nonce is exactly 32 bytes, and each BLAKE3 nonce commitment is exactly 32 bytes. Both
roles generate their nonce before receiving any peer nonce. The initiator creates the
pairing ID. `PairingRequest` and `PairingResponse` exchange only commitments;
`PairingReveal` discloses a nonce only after both commitments are fixed. Each role sends its
reveal before waiting for the peer reveal. Hello already carries authenticated identity and
bounded display metadata.

```text
Initiator                         Responder
    |                                 |
 generate ID + nonce              generate nonce
    |                                 |
    |--- PairingRequest(commit) ----->|
    |<-- PairingResponse(commit) -----|
    |                                 |
    |------ PairingReveal(nonce) ---->|
    |<----- PairingReveal(nonce) -----|
    |                                 |
    | verify responder commitment     | verify initiator commitment |
    |                                 |
    |      derive same SAS code       |
    |                                 |
 local confirm                    local confirm
    |                                 |
    |------ PairingDecision --------->|
    |<----- PairingDecision ----------|
    |                                 |
 durable trust                    durable trust
    |                                 |
    |------ PairingComplete ---------->|
    |<----- PairingComplete -----------|
    |                                 |
             Authorized
```

Each nonce commitment is BLAKE3 over the following exact byte concatenation:

```text
UTF-8 "rift-pairing-commitment-v1"
protocol version as two-byte unsigned big-endian (0x0001)
role as one byte (initiator 0x00, responder 0x01)
initiator DeviceId (32 bytes)
responder DeviceId (32 bytes)
pairing ID (16 bytes)
role's nonce (32 bytes)
```

The role, authenticated identities, and pairing ID prevent a commitment from being reused
across roles, peers, or attempts. A reveal that does not reproduce the sender's prior
commitment fails pairing and closes the disposable connection before the SAS is exposed.
Because neither role learns the peer nonce before fixing its own commitment, a responder
cannot cheaply search candidate nonces for a chosen six-digit SAS after seeing the
initiator nonce.

The canonical SAS transcript is the following exact byte concatenation; it does not use
Rust memory layout or Postcard encoding:

```text
UTF-8 "rift-pairing-v1"
protocol version as two-byte unsigned big-endian (0x0001)
initiator DeviceId (32 bytes)
responder DeviceId (32 bytes)
pairing ID (16 bytes)
initiator nonce (32 bytes)
responder nonce (32 bytes)
```

The SAS digest is BLAKE3 over that concatenation. Interpret digest bytes 0 through 3 as
an unsigned big-endian `u32`, reduce modulo 1,000,000, and render it as exactly six
zero-padded decimal digits. This value is a human comparison code, not a password or
credential. Both roles retain the initiator/responder ordering and therefore derive the
same code. The machine-readable vectors include a complete transcript and expected code.

After both nonce reveals are verified and the code is derived, each role waits for an
explicit local decision. A received `accepted = true` never substitutes for local
confirmation. Both decisions must be true. Each side then durably persists the
authenticated peer's `DeviceId`, name, and platform before sending `PairingComplete`;
authorization is returned only after both completion messages have been exchanged. A
false decision rejects the attempt without persisting a revocation or trust record.

Each network phase has a separate nonzero pairing deadline. A timeout, wrong pairing ID,
commitment mismatch, duplicate or out-of-order message, unexpected Ping/Pong, framing
failure, or transport failure invalidates the disposable connection and creates no new
trust. Pairing attempts and nonce material are ephemeral and are not replayed after
connection loss. Fresh attempts use a fresh pairing ID and both fresh nonces.

Durable trust is local, so final completion is not a distributed transaction. A crash or
network loss around final commit can leave one side trusted while the other remains
unknown. This fails safely: the unknown side still refuses authorization, and the pair
can be explicitly reconciled later.

## Authentication and authorization boundary

Iroh QUIC authentication answers:

> Which public endpoint identity authenticated this connection?

Hello binding answers:

> Does the peer's Rift application identity claim the same public identity?

Neither answer is authorization. After bootstrap, ConnectionIntent declares what the
dialer wants. Local durable policy decides whether that purpose is permitted: only
Trusted + AuthorizedSession and Unknown + Pairing are admitted. All other combinations
are rejected. No network message directly creates trust; `Unknown -> Trusted` requires
an explicit local confirmation API call.

The complete pairing sequence is Hello → Pairing intent accepted → PairingRequest /
PairingResponse / PairingReveal / PairingDecision / PairingComplete. Authorized reconnect
uses Hello → AuthorizedSession intent accepted → canonical application session, without
pairing or feature replay.

## Conformance vectors

The machine-readable wire contract is in
[`v1-vectors.json`](v1-vectors.json). It contains the semantic message fields, the
Postcard payload bytes, and the complete length-prefixed frame bytes in lowercase
hexadecimal. The vectors cover Unicode metadata, empty and non-empty capabilities, Hello,
Ping, Pong, every pairing message kind, and one complete commitment/transcript/SAS result.
Tests reconstruct every semantic value and assert exact payload/frame, commitment, or code
equality. The M2 Hello/Ping/Pong vectors remain byte-for-byte unchanged.

## M5 explicit connection purpose

After the symmetric identity-bound Hello, the dialer sends exactly one
`ConnectionIntent { purpose }`; the acceptor replies with one
`ConnectionIntentResult { accepted }`. Only then can pairing or an authorized
application session begin. These append Postcard message discriminants **8** and
**9**. Purpose discriminants are **0** AuthorizedSession and **1** Pairing. Boolean
results encode as 0/1. Old message discriminants 0–7 and all old vector bytes remain
unchanged. Exact two-byte payloads and six-byte frames are appended to v1-vectors.json.

| Local durable state | AuthorizedSession | Pairing |
| --- | --- | --- |
| Trusted | authorized | reject |
| Unknown | reject | pairing-only |
| Revoked | reject | reject |

Both directions apply this policy in `rift-session`; outbound callers must choose a
purpose. Remote rejection communicates only `accepted: false`, never the remote
trust state or a reason string. There is no fallback from Session to Pairing and
no automatic re-pairing after asymmetric forget or final-commit failure.

The transport uses the configured Hello/control deadline for intent reads/writes.
Unexpected messages, invalid purpose/result bytes, truncation, timeout, and repeated
local gate operations poison and close the disposable connection. A rejected
acceptor allows a bounded interval for the dialer to receive the result and close,
rather than immediately discarding buffered QUIC data. Dropping a bootstrapped
connection closes it, including cancellation before admission completes.

## M6 metadata foundation (runtime not yet enabled)

`rift-core::TransferId` is a transparent 16-byte value. Postcard encodes the raw
array without a length prefix. Display and text parsing use exactly 32 lowercase
ASCII hexadecimal characters; uppercase, whitespace, and alternate spellings are
rejected. Runtime session IDs remain separate. The eventual daemon generator must
use the OS CSPRNG and check collisions; the domain type performs no OS operations.

`TransferMetadata` serializes, in order, a `TransferFileName`, a `u64` byte length,
and 32 raw BLAKE3 bytes. The length is at most **1 TiB**, with zero explicitly valid.
Construction and deserialization enforce the same limits. The future daemon's
configured acceptance limit must additionally constrain incoming and outgoing files.

The filename is a presentation component of **1–255 UTF-8 bytes**, validated before
owned allocation. It rejects slash, backslash, ASCII controls (including NUL and DEL),
Windows-invalid `< > : " | ? *`, trailing dots/spaces, and reserved Windows device
basenames, case-insensitively, including extension forms. COM/LPT digits 1–9 and
Windows' superscript ¹/²/³ forms are reserved. `.` and `..` are invalid. Other Unicode
is permitted without normalization. This type is not permission to select a directory
or write a file; receiver staging and explicit acceptance are separate runtime duties.
No source path, mode, ownership, timestamps, or other filesystem metadata is encoded.

The metadata and wire codecs below are implemented, but the daemon transfer runtime,
authorized data-stream APIs, persistence, and IPC are not yet implemented.
`BLOB_TRANSFER_V1` remains unadvertised until that runtime initializes successfully.

## M6 single-file transfer wire contract

This is an additive pre-release v1 extension; control framing stays at 1 MiB and
existing discriminants **0–9** and conformance vector objects are unchanged.

| Index | Control message | Fields in Postcard order |
| --- | --- | --- |
| 10 | `TransferOffer` | `TransferId`, `TransferMetadata` |
| 11 | `TransferAccept` | `TransferId`, `offset: u64` |
| 12 | `TransferTerminal` | `TransferId`, `TransferTerminalStatus` |
| 13 | `TransferTerminalAck` | `TransferId` |

`TransferTerminalStatus` indices are 0 Completed, 1 Rejected, 2 Cancelled, and
3 Failed followed by `TransferFailureCode`. Failure indices are 0 Integrity,
1 SourceChanged, 2 Io, 3 Resource, 4 Protocol. These contain no paths, errno strings,
stack traces, or filesystem diagnostics. Unsupported enum indices are rejected.
Transfer control messages are never accepted as pairing messages.

### Authorization and acceptance

A runtime implementing this contract advertises capability **1**, `BLOB_TRANSFER_V1`,
only after successful transfer-state initialization. Outbound transfer requires the
peer's authorized Hello to advertise it; absence is an unsupported-capability result,
not a reason to disconnect a valid session. Transfer traffic from a peer that did not
advertise support is a session protocol violation. Pairing-only peers cannot use the
data plane even when their Hello advertises the capability.

Trust permits an offer, not writing a payload. The receiver must explicitly accept
locally, persist that decision, and reserve bounded receive-worker capacity before
sending Accept. File bytes never enter control messages. The daemon owns the logical
transfer; its sole session control reader/writer dispatches messages by transfer ID.

### Independent data header

One send attempt or resume uses one fresh **unidirectional** QUIC stream:

```text
4-byte big-endian header payload length (at most 256)
Postcard DataStreamHeader::BlobV1 (enum index 0):
    TransferId (16 raw bytes)
    offset (u64)
    remaining_len (u64)
raw suffix bytes
clean QUIC FIN
```

The dedicated header bound is **256 bytes**, not the control-frame bound. The codec
checks it before reading payload and uses a fixed 256-byte receive buffer. Header
Postcard decoding must consume the whole declared header; attached header garbage,
unknown kind/version, truncation, and oversized length fail explicitly. Header readers
do not consume raw file bytes. The stream owner imposes a header deadline and stops
an attempt on cancelled partial framing rather than trying to restart that parser.

The implied `offset + remaining_len` may not overflow or exceed 1 TiB. Against the
immutable metadata, the receiver must also require:

```text
offset <= total_len
remaining_len == total_len - offset
```

`DataStreamHeader::validate(total_len)` enforces these numeric invariants. Runtime
validation must additionally match the peer, ID, incoming direction, durable local
acceptance, current durable offset, and exclusive active attempt generation.

The receiver reads exactly `remaining_len` raw bytes, then requires clean FIN. Short
clean EOF and extra bytes are terminal length/protocol failures; a reset due to session
loss is a pause candidate. Whole-file BLAKE3, including any resumed prefix, must match
before publication. Zero-byte files can complete after verifying the empty digest
without requiring a payload stream. A full durable prefix can likewise be verified
without retransmitting bytes.

### Required sequencing and replay behavior

The following runtime semantics are the contract to be implemented, not evidence that
this protocol-only checkpoint already transfers files.

```text
Outgoing: prepare → queue → offer → accept → send suffix → terminal → ack
Incoming: pending offer → durable accept → receive → verify/publish → terminal → ack
                         ↘ durable reject → terminal → ack
Active transfer → connection loss → paused → replay offer → accept offset → new attempt
Active transfer → cancel/fail → durable terminal → terminal → ack
```

Transfers are keyed by `(peer DeviceId, TransferId)`, with immutable metadata. Duplicate
Offer with matching metadata while pending must not prompt twice. After acceptance or
pause it returns the current durable offset. After terminal state it replays Terminal.
The same key with different metadata is a session protocol violation. Unknown Accept,
impossible offsets, data before acceptance, and duplicate simultaneous streams are
also session protocol violations, not permission to allocate another worker.

Terminal is persisted before transmission and replayed until acknowledged. Duplicate
Terminal receives another Ack. Unknown Terminal is acknowledged and otherwise ignored,
allowing cleanup after the local runtime has forgotten a settled record. Ack before a
local terminal state is illegal. Terminal processing is idempotent and cannot resurrect
a cancelled transfer. A locally completed file is never overwritten by a replay.

#### Happy path

```text
Sender                                      Receiver
Offer(id, metadata) ------------------------> persist pending; local prompt
                                            local accept; persist acceptance
                   <------------------------ Accept(id, durable offset)
new uni stream: header + suffix + FIN -----> exact length + full BLAKE3
                                            flush/sync, atomic promotion,
                                            directory sync, persist Completed
                   <------------------------ Terminal(id, Completed)
TerminalAck(id) ---------------------------> settle protocol state
```

#### Reject

```text
Sender                                      Receiver
Offer ------------------------------------> local reject; persist Rejected
                   <------------------------ Terminal(Rejected)
TerminalAck ------------------------------> settle; no payload or staging
```

#### Cancel (either side)

```text
Cancelling peer                             Other peer
persist Cancelled; stop/reset worker
Terminal(Cancelled) -----------------------> stop worker; delete incomplete staging
                    <----------------------- TerminalAck
```

Cancellation never modifies/deletes the sender's source. Incomplete receive staging
is deleted on terminal cancellation/failure, but preserved on resumable connection loss.
Completion/integrity and cancellation races require daemon generation fencing.

#### Connection loss and resume

```text
Sender                                      Receiver
header + partial suffix ------------------> staged prefix
                 connection lost; old workers cancelled/joined
                 reconnect, fresh authorized session and Hello
Offer(same ID, same metadata) -------------> inspect/sync durable partial length
                    <----------------------- Accept(same ID, nonzero offset)
new header + remaining suffix + FIN ------> rehash prefix; verify whole file
                    <----------------------- Terminal(Completed)
TerminalAck ------------------------------> settle
```

Connection replacement does not change TransferId or immutable metadata. The receiver's
actual durable partial length, not cached sender progress, determines offset. BLAKE3
internal state is not serialized: resume rehashes the prefix with a fixed 64 KiB buffer.
Source mutation under the same ID is terminal SourceChanged. Integrity failure or local
I/O failure may remain transfer-local when framing is valid; impossible state/header
invariants close the session. Live Iroh path migration alone requires no replay.

Exact vectors cover the offer, zero/nonzero acceptance, all terminal/failure values,
acknowledgement, and zero/resumed data headers. Tests retain an immutable M5 fixture and
check the old vector objects byte-for-byte, as well as decoding all current vectors.
